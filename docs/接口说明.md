# 逆向笔记：完美校园「用电支出 → 剩余电量」

记录这个项目依赖的接口细节、加密链路，以及踩过的坑。文中的标识符一律用占位符，
复现时换成你自己的。

## 结论先行

剩余电量在 `getRoomState.do` 返回 JSON 的 `quantity` 字段，单位看 `quantityunit`
（电是「度」，水是「吨」）。取到它需要两步：先拿到一个有效的 wanxiao token，
再走 CloudPayment 的五步链。

## 先分流：你的学校走哪条产品线

新开普有两代水电接口，先确定自己学校在哪条上：

| | 老引擎 SWAEServlet | CloudPayment |
| --- | --- | --- |
| 域名 | `xqh5.17wanxiao.com/smartWaterAndElectricityService/SWAEServlet` | `h5cloud.17wanxiao.com:18443/CloudPayment/` |
| 鉴权 | **不需要 token**，只校验学校代码 + 学号 | 需要 wanxiao token 换 SESSION |
| 本项目 | 未实现（此路只对部分学校成立） | 已实现 |

判断方法：直接问老引擎。返回 `existflag:"0"` / 未绑定房间，说明你们学校的宿舍电表
不挂这代系统，走 CloudPayment（也就是本项目走的路）。

## 登录协议

`wanxiao_login.py` 完整复刻了 App 的登录，纯 Python，只依赖 `cryptography`：

```
RSA-1024 自生成密钥对
  -> exchangeSecretkey.action  { "key": <SPKI DER 的 base64，每 64 字符换行> }
  -> 用私钥 PKCS#1 v1.5 解密响应，得到 { session, key(32hex) }，appKey = key[:24]
  -> 之后所有业务体：3DES-CBC(IV=b"66666666", PKCS#5) + base64
  -> 外层信封恒为 { "session": sid, "data": <b64> }，Content-Type: application/text
  -> 请求头 campusSign = sha256(请求体原文).hexdigest()
  -> password 字段是**逐字符**分别 3DES 加密后 base64 的数组
```

基址 `https://app.17wanxiao.com/campus`。

### token 到底是什么（这里最容易错）

**CloudPayment 认的 token = 本次登录所用的那一次「握手 session」，
不是响应体里的 `user.token`。**

抓包铁证：App 登录包信封里的 `session=<UUID-A>`，随后原样出现在
`pay.do?token=<UUID-A>` 上。而响应体里的 `user.token` 前 36 位是**账号级固定值**
（短信登录和密码登录返回同一个），拿它去 SSO 会被拒。

### 新设备风控与一次性绑定

未绑定的 `deviceId` 调 `loginnew.action` 会回：

```
code_=5 您正在新设备上使用完美校园，请使用验证码进行验证登录
```

这个校验在密码校验**之前**，所以不会消耗密码错误次数（`code_=5` 也用于
「密码错误,您还有N次机会」，别看码就下结论）。

绑定的唯一途径：

```
gainMatrixCaptcha543.action          发短信
registerUsersByTelAndLoginNew.action 提交验证码，同时把本机 deviceId 绑成受信设备
```

两个必须注意的点：

1. **必须带 `543` 后缀。** 不带 543 的 `gainMatrixCaptcha.action` 也会回
   「聚合验证码发送成功」，但发的不是同一条短信，提交必然
   `短信验证码错误 code_=800114003`。这个坑非常隐蔽。
2. 验证码绑在发起那次握手的 session 上，所以发短信和提交验证码
   **必须复用同一个 session + appKey**（代码里的 `_reuse_or_handshake`）。

参数集：`appCode / deviceId / mobile / netWork / qudao / requestMethod / shebeixinghao /
sms / systemType / telephoneInfo / telephoneModel / type:"2" / wanxiaoVersion`，
**不能带 `action` 和 `confirm`**。验证码额度是每天 100 次。

绑定成功后，实测**换一个 IP 也不会再要验证码**（风控只看 deviceId），所以服务器可以
完全无人值守地自己续 token。这也是本项目能在 VPS 上跑起来的前提。

## CloudPayment 取数链

基址 `https://h5cloud.17wanxiao.com:18443/CloudPayment/`，全部 GET。

```
1  user/pay.do?versionnum=…&customerId=<schoolcode>&systemType=Android
     &UAinfo=wanxiao&versioncode=…&token=<握手session>     → 302 并下发 HttpOnly SESSION
2  bill/type.do
3  bill/querySelfPayList.do            → payprolist（用电支出 / 购冷水支出）
4  bill/selectPayProject.do?txcode=…&payProId=…&…          → 建立会话上下文
5  user/getRoomState.do?payProId=…&schoolcode=…
     &businesstype=2&roomverify=<校区-楼栋--楼层-房间>
     → {"returncode":"100","quantity":"110.0","quantityunit":"度","description":"616"}
```

每个请求都要带：

```
X-Requested-With: XMLHttpRequest
Accept: application/json, text/javascript, */*; q=0.01
User-Agent: <App 内嵌 WebView 的 UA，不是 OkHttp 的 Dalvik UA>
Referer: <第 4 步那条完整的 selectPayProject URL>
```

### 三个隐蔽要求

**Referer 参与鉴权。** 服务端是从 `Referer` 里的 `payProId` 反查房间序列号
`idserial` 的。缺了第 4 步或 Referer 不对，`getRoomState` 返回的是 Java 的
`toString`：

```
RspBaseVO [code=ERROR, msg=系统繁忙，请稍后重试]
```

这个错误信息极具误导性，看起来像服务端挂了或者鉴权失败，实际只是少了一步上下文。

**Cookie 必须用真正的 CookieJar。** `pay.do` 是先 302 再在**这一跳**下发 SESSION 的，
手工解析最终响应的 `Set-Cookie` 会把它整条丢掉，表现是「明明登录成功却永远查不到数据」。

**token 有效性只能靠项目列表判断。** token 无效时服务端**不报错**，照样发一个匿名
SESSION，返回 200 HTML，`querySelfPayList` 的 `payprolist` 为 `null`。所以唯一可靠探针是
「项目列表非空」。

### 房间树

只知道门牌号时用 `user/getRoom.do` 下钻：

```
user/getRoom.do?payProId=…&schoolcode=…&businesstype=2
    &optype=1|2|3|4&areaid=&buildid=&unitid=&levelid=
```

`optype` 是层级：1 校区、2 楼栋、3 单元/楼层、4 房间，逐层带上父级 id。

> **坑：** `optype=4` 返回的 `id` **已经是拼好的 `roomverify`**（形如
> `101-07--112-308`），不要再自己拼一遍，否则会双重包装查不到东西。
> 中间的 `--` 是「单元为空」留下的分隔符。

整棵树几百个节点，务必用校区/楼栋名剪枝。

## 已排除的免登录路线

- 老引擎 SWAEServlet 确实不需要 token，本校前置机也存活并回 `获取成功！`，
  但返回 `existflag:"0"` / 未绑定房间 —— 宿舍电表不挂这代系统，此路不通。
- CloudPayment 自身**没有任何 login 接口**（全量 JS 里只有 `checkRoomCount` /
  `getRoom` / `getRoomState`），所以必须持有有效 wanxiao token。

结论：没有免登录捷径，但「绑定后账密自主登录」这条足够稳。

## 踩过的坑清单

1. 用 `user.token` 当 CloudPayment 的 token —— 会被拒，且失败形态是空数据而非报错。
2. 以为必须先调 `checkRoomCount.do` —— 真正缺的上下文是 `selectPayProject.do` + Referer。
3. 手工解析 `Set-Cookie` 而不是用 CookieJar —— 丢掉 302 那一跳的 SESSION。
4. 用不带 543 的验证码接口 —— 短信发出去了但不是同一条链路，提交必然失败。
5. 发短信和提交验证码之间重新握手 —— 验证码和 session 是绑定的。
6. 部分接口返回 gzip 而 urllib 不解压；mitmproxy 里也有响应声明 gzip 但内容非法的情况。
7. 把用电量整笔记在采样时刻所在的天 —— 跨 0 点的那一笔会记错，本项目按时长比例摊。

## 抓包环境（可选）

如果要在 Android 模拟器上复现抓包，有两个坑：

**其一，App 启动即崩。** 某个安全 SDK 的 `JNI_OnLoad` 在 arm64→x86_64 native bridge 下
确定性 SIGSEGV 并无限重启。把那个 `.so` 改名让 App 加载不到它就正常了：

```bash
adb -s 127.0.0.1:7555 root
adb -s 127.0.0.1:7555 shell 'cd /data/app/~~*/<包名>-*/lib/arm64 && mv libSdkHelper_core.so libSdkHelper_core.so.off'
```

代价是少了点 SDK 功能，但「缴费 → 用电支出」页面照常出数。

**其二，抓 https。** 模拟器是 userdebug、adbd 可 root、SELinux Permissive，但 `/system`
只读。只装用户 CA 不够（App 走 native 网络栈时不看用户信任库），得塞进系统目录。
`/system/etc/security/cacerts` 是只读分区里的目录，用 bind mount 覆盖：

```bash
# c8750f0d.0 = mitmproxy CA 的 subject_hash_old
adb shell "cp -r /system/etc/security/cacerts /data/local/tmp/cacerts"
adb push mitmproxy-ca-cert.pem /data/local/tmp/cacerts/c8750f0d.0
adb shell "mount -o bind /data/local/tmp/cacerts /system/etc/security/cacerts"
adb shell "settings put global http_proxy 10.0.2.2:8080"
```

用完一定卸载，否则系统信任库里永远留着一个能解密你全部流量的根证书：

```bash
adb shell "settings delete global http_proxy"
adb shell "umount /system/etc/security/cacerts"
```

## 关于静态脱壳

`classes.dex` 是 360 加固的高熵密文，真实 dex 在运行时才解密，静态不可读；
`assets/` 下部分资源是 1 字节占位。arm64 模拟器上 jiagu 在 native translation 层会
确定性 SIGSEGV，动态脱壳也没走通。

最终没有从 APK 里抠出协议，而是**抓包 + 读 H5 前端 JS** 反推出来的。这类混合 App 的业务
逻辑大量放在 H5 里，前端 JS 是明文，比脱壳便宜得多。

## 隐私提醒

这套接口的设计存在明显的越权读取面：老引擎只校验「学校代码 + 学号」，而 CloudPayment 的
token 一旦泄露，等于交出登录态（姓名、证件号、手机号、绑定的房间都能读）。

所以：只用它查自己的账号；不要拿它做批量探测；不要把 token、`deviceId`、`config.json`
提交进仓库或贴进群里。发现接口存在鉴权缺陷，负责任的作法是报给学校网络中心，
而不是拿去验证别人能不能查。
